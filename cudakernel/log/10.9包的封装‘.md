# CUDA 推理算子库工程化总结：从 CUDA Extension 到 Python 包

这次我们完成了 `cudakernel` 项目从单一 C++/CUDA 扩展向 Python 算子库结构迁移的关键步骤。过程中遇到了三个核心问题：Python 包与扩展模块命名冲突、Python 模块搜索路径错误、PyTorch 动态库版本冲突，并分别找到了对应的解决方案。

这份总结可以作为后续开发 CUDA 推理库时的工程记录。

## 一、工程目标与最终架构

我们的目标不是只编写一组独立的 CUDA kernel，而是构建一个可以在 Python 中像 PyTorch 一样调用的推理算子库，为后续实现 Transformer、Qwen 模型和简化版 vLLM 打基础。

整个工程采用分层结构：

模型层：`layers.py`

Linear、RMSNorm、Attention、Transformer Block

Python 算子接口：`ops.py`

参数组织、调用底层扩展

C++ 绑定层：`bindings.cpp`

PyTorch Tensor 接口、参数检查、函数注册

CUDA 实现层：`.cu` 文件

add、mul、RMSNorm、Softmax、RoPE，以及后续 GEMM

各层职责需要清晰分开：

* CUDA 层负责真正的 GPU 计算。

* C++ 绑定层负责将 CUDA 实现暴露给 Python，并处理 Tensor 接口。

* `ops.py` 提供便于调用的函数接口。

* `layers.py` 将算子组织为可复用的模型组件。

这样，底层 kernel 可以独立优化，上层 Transformer 不必关心线程块、共享内存或 Tensor Core 的具体实现。

## 二、最终项目目录

我们将编译扩展改为 `_C`，并把它放入 Python 包目录中。

```
cudakernel/
├── setup.py
├── bindings.cpp
├── add.cu
├── mul.cu
├── rmsnorm.cu
├── softmax.cu
├── rope.cu
└── inference/
    ├── __init__.py
    ├── ops.py
    ├── layers.py
    ├── _C.cpython-310-x86_64-linux-gnu.so
    └── test.py
```

各文件的作用如下：

| 文件                      | 职责                          |
| ----------------------- | --------------------------- |
| `setup.py`              | 配置 Python 包与 C++/CUDA 扩展的构建 |
| `bindings.cpp`          | 注册扩展函数，让 Python 可以调用 C++ 接口 |
| `add.cu`、`mul.cu` 等     | 实现具体 CUDA kernel 及其调用封装     |
| `inference/_C.so`       | 编译生成的二进制扩展模块                |
| `inference/ops.py`      | 封装底层扩展函数                    |
| `inference/layers.py`   | 定义模型级 Python 类              |
| `inference/__init__.py` | 统一导出公共接口                    |
| `inference/test.py`     | 验证导入与算子调用                   |

这里的 `.so` 文件名包含 `cpython-310`，表示它针对 CPython 3.10 构建。它不是普通的 Python 源文件，而是可以由 Python 导入的编译扩展。

## 三、问题一：Python 包名与扩展模块名冲突

### 1. 原来的配置

最初的 `setup.py` 使用：

Python

运行

```
CUDAExtension(
    name="inference",
    sources=[
        "bindings.cpp",
        "add.cu",
        "mul.cu",
        "rmsnorm.cu",
        "softmax.cu",
        "rope.cu"
    ]
)
```

编译后生成：

```
inference.cpython-310-x86_64-linux-gnu.so
```

这种方式适合将整个扩展作为一个模块直接导入：

Python

运行

```
import inference
```

但是，我们接下来希望创建 `inference/` Python 包，并在其中编写 `ops.py` 和 `layers.py`。

如果 Python 包和二进制扩展都叫 `inference`，导入解析容易发生冲突，也不利于组织更复杂的项目。

### 2. 解决方案：区分发行包名和扩展模块名

我们修改为：

Python

运行

```
setup(
    name="inference",
    packages=find_packages(),
    ext_modules=[
        CUDAExtension(
            name="inference._C",
            sources=[
                "bindings.cpp",
                "add.cu",
                "mul.cu",
                "rmsnorm.cu",
                "softmax.cu",
                "rope.cu"
            ],
            extra_compile_args={
                "cxx": ["-O3"],
                "nvcc": ["-O3", "-arch=sm_89", "-Xptxas=-v"]
            }
        )
    ],
    cmdclass={"build_ext": BuildExtension}
)
```

这三个名字的含义不同：

* `name="inference"`：Python 发行包名称。

* `packages=find_packages()`：将项目中的 Python 包纳入构建配置。

* `CUDAExtension(name="inference._C")`：指定编译扩展的完整模块名。

这样，Python 包负责组织 API，`_C` 则专门负责底层 C++/CUDA 计算。

### 3. 绑定层也需要匹配

在 `bindings.cpp` 中应使用：

C++

```
PYBIND11_MODULE(TORCH_EXTENSION_NAME, m)
```

这允许构建系统将正确的扩展模块名传给绑定代码。不要将模块名硬编码成旧名称 `inference`。

工程经验： 当一个项目同时包含 Python API 和编译扩展时，使用 `inference` 与 `inference._C` 这样的命名分层，能避免后续扩展 API 时的命名冲突。

## 四、问题二：`ModuleNotFoundError: No module named 'inference'`

我们最初在包目录内运行：

Bash

```
cd ~/infra-project/cudakernel/inference
python test.py
```

出现：

```
ModuleNotFoundError: No module named 'inference'
```

之后回到项目根目录运行：

Bash

```
cd ~/infra-project/cudakernel
python inference/test.py
```

仍然遇到相同错误。

### 1. 为什么会发生？

Python 的模块搜索路径与脚本的启动方式有关。

直接执行：

Bash

```
python inference/test.py
```

时，Python 通常将脚本所在的目录放在 `sys.path` 的开头，也就是：

```
.../cudakernel/inference/
```

但我们要导入的是这个目录的父级下的 `inference` 包：

```
.../cudakernel/inference/
```

所以需要确保包的父目录 `cudakernel/` 出现在模块搜索路径中。

### 2. 最终解决方案

我们使用：

Bash

```
python -m inference.test
```

并在项目根目录执行。

这样 Python 会以模块方式加载 `inference.test`，从项目根目录解析 `inference` 包。

当测试程序需要通过 `import inference` 导入当前开发中的包时，这种运行方式清晰且适合当前项目。

### 3. 如何确认导入的是正确模块？

我们执行了：

Bash

```
python -c "import torch; import inference; print(torch.__version__); print(inference.__file__); print(inference._C.__file__)"
```

得到的结果包含：

```
2.4.1+cu121
/home/ljc/infra-project/cudakernel/inference/__init__.py
/home/ljc/infra-project/cudakernel/inference/_C.cpython-310-x86_64-linux-gnu.so
```

这说明 Python 已经找到项目中的 `inference` 包，而且成功加载了包里的 `_C` 扩展。

工程经验： 开发阶段应当明确项目根目录与 Python 包目录的关系，区分“找不到包”和“找到包后加载扩展失败”这两类错误。

## 五、问题三：`libtorch_cpu.so: undefined symbol`

这是整个过程中最值得记录的问题。

当 Python 找到 `inference` 包后，报错变成：

```
ImportError: /usr/lib/x86_64-linux-gnu/libtorch_cpu.so:
undefined symbol: _ZN4gloo10rendezvous5StoreD2Ev
```

这表明问题已经不再是 Python 包搜索路径，而是在导入二进制扩展时加载动态库失败。

### 1. 先验证 PyTorch 本身

我们检查了版本和安装位置：

Bash

```
python -c "import torch; print('version:', torch.__version__); print('path:', torch.__file__); print('CUDA:', torch.version.cuda)"
```

结果：

```
version: 2.4.1+cu121
path: /home/ljc/.conda/envs/Qwen/lib/python3.10/site-packages/torch/__init__.py
CUDA: 12.1
```

接着测试 GPU：

Bash

```
python -c "import torch; print(torch.ones(1, device='cuda'))"
```

结果：

```
tensor([1.], device='cuda:0')
```

说明 Conda 环境里的 PyTorch 可以正常使用 GPU。

### 2. 使用 `ldd` 发现真正的问题

执行：

Bash

```
ldd inference/_C.cpython-310-x86_64-linux-gnu.so | grep -E "torch|gloo|not found"
```

却发现它解析到了系统目录：

```
/usr/lib/x86_64-linux-gnu/libtorch_cpu.so
/usr/lib/x86_64-linux-gnu/libtorch_python.so
/usr/lib/x86_64-linux-gnu/libtorch.so.2.6
/usr/lib/x86_64-linux-gnu/libtorch_cuda.so.2.6
/lib/libgloo.so.0
```

这与当前 Conda 环境中的 PyTorch 2.4.1 不一致。

扩展在加载时混入了系统目录中的另一套 PyTorch 动态库，导致符号解析失败。

### 3. 解决方案：调整动态库搜索顺序

我们执行：

Bash

```
export LD_LIBRARY_PATH="$CONDA_PREFIX/lib/python3.10/site-packages/torch/lib:$CONDA_PREFIX/lib:$LD_LIBRARY_PATH"
```

它将当前 Conda 环境的 PyTorch 库目录放在搜索路径前面。

之后再运行：

Bash

```
python -c "import torch; import inference; print(torch.__version__); print(inference.__file__); print(inference._C.__file__)"
```

成功输出了 PyTorch 版本、Python 包路径和扩展路径。

### 4. 为什么不直接重新编译？

因为现有证据显示，PyTorch 本身和 GPU 都正常，错误集中在运行时动态库解析。

此时应先检查：

Bash

```
ldd inference/_C.cpython-310-x86_64-linux-gnu.so
```

以及：

Bash

```
readelf -d inference/_C.cpython-310-x86_64-linux-gnu.so | grep -E 'NEEDED|RPATH|RUNPATH'
```

确认实际加载的依赖，再决定是否重新编译。重新编译并不必然能修复运行时加载了错误动态库的问题。

## 六、问题四：每次手动设置动态库路径太麻烦

前面使用 `export` 可以临时修复，但新开终端或重新进入环境后，不一定会保留设置。

因此，我们把它写进 Conda 环境的激活脚本。

### 1. 创建脚本目录

Bash

```
mkdir -p "$CONDA_PREFIX/etc/conda/activate.d"
mkdir -p "$CONDA_PREFIX/etc/conda/deactivate.d"
```

### 2. 激活脚本

文件位置：

```
$CONDA_PREFIX/etc/conda/activate.d/torch-libs.sh
```

内容：

Bash

```
export _OLD_LD_LIBRARY_PATH="${LD_LIBRARY_PATH-}"
export LD_LIBRARY_PATH="$CONDA_PREFIX/lib/python3.10/site-packages/torch/lib:$CONDA_PREFIX/lib${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"
```

当执行 `conda activate Qwen` 时，它会自动优先搜索当前环境中的 PyTorch 库。

### 3. 停用脚本

文件位置：

```
$CONDA_PREFIX/etc/conda/deactivate.d/torch-libs.sh
```

内容：

Bash

```
if [ "${_OLD_LD_LIBRARY_PATH+x}" = x ]; then
    export LD_LIBRARY_PATH="$_OLD_LD_LIBRARY_PATH"
    unset _OLD_LD_LIBRARY_PATH
else
    unset LD_LIBRARY_PATH
fi
```

这样退出环境时，可以恢复激活前的动态库路径。

### 4. 验证结果

我们已经执行：

Bash

```
conda deactivate
conda activate Qwen
echo "$LD_LIBRARY_PATH"
```

实际输出：

```
/home/ljc/.conda/envs/Qwen/lib/python3.10/site-packages/torch/lib:/home/ljc/.conda/envs/Qwen/lib
```

说明激活脚本已生效。

需要注意：这个脚本假设当前环境使用 Python 3.10。以后升级 Python 或更换环境时，应检查路径是否仍然正确。

## 八、后续开发建议

在继续开发 Transformer 推理库时，可以遵循以下顺序。

1. 完善算子接口。 在 `ops.py` 中统一 `add`、`mul`、RMSNorm、Softmax、RoPE 的参数接口，并与 `bindings.cpp` 实际注册的签名保持一致。

2. 建立逐算子测试。 针对 FP32、BF16、不同张量形状、非连续张量和边界情况进行正确性验证；只测试已实现的功能，不要假设所有算子都支持所有类型。

3. 构建模型组件。 将有参数的算子封装为 `nn.Module`，例如 `RMSNorm` 和后续的 `Linear`；无状态操作可以先保留为函数。

4. 实现 GEMM。 Transformer 的线性层依赖矩阵乘法。建议先明确 `linear(x, weight, bias)` 的接口，再将它连接到自定义 GEMM kernel。

5. 组合 Transformer Block。 在算子正确性得到验证后，再组织 Attention、MLP、归一化和位置编码，逐步接入 Qwen 模型。

最后总结一下本次工程化的核心经验：Python 导入问题、C++/CUDA 扩展加载问题和 CUDA kernel 计算问题是不同层次的问题，应当分别定位。 先检查模块路径，再检查动态库依赖，最后才进入 kernel 的数值正确性与性能调试。这样可以避免把工程配置问题误判成 CUDA 算法错误。
